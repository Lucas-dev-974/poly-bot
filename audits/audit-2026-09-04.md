# Rapport d'audit — polymarket-reverse-arbitrage-bot v2.0.0

**Date** : 2026-09-04
**Auditeur** : Hermes Agent (glm-5.2)
**Périmètre** : 21 fichiers TS backend (`src/`), 30 fichiers TSX/TS frontend (`frontend/src/`), DB SQLite, docs. Builds vérifiés : `npm run build` ✅ et `npm --prefix frontend run build` ✅ passent tous les deux.

---

## Vue d'ensemble

Le projet est **bien structuré et globalement sain**. Points forts :

- **Séparation des responsabilités propre** : scanner → strategy → tracker → resolver → broker/ledger, avec le dashboard en simple consommateur SSE (backend-side, pas de logique dans le frontend).
- **Garde-fous de trading sérieux** : exposure cap, max open per side, depth check, favorite validation, pair cost check, stale order cleanup. Le code de gestion des ordres live GTC (posted orders → poll → finalize → position) est le plus soigné du projet, avec des commentaires qui expliquent *pourquoi* (rares et précieux).
- **Persistence cohérente** : chaque repo SQLite a son miroir mémoire, `loadFromDb` recharge tout au démarrage.
- **Commentaires de qualité inégale mais souvent excellents** — notamment `position-resolver.ts` qui documente les pièges réels de l'API Gamma (strings JSON, seuils 0.99/0.01, `/events` vs `/markets`).

## 🔴 Bugs critiques (sécurité)

### 1. La clé privée est servie au frontend — `server.ts:194`

```ts
// handleState()
JSON.stringify({ config: this.config, events: bus.replay() })
```

`/api/state` renvoie la **config complète, y compris `privateKey`**. Le frontend l'appelle au mount (`api.state()` → `loadInitialState` → `App.tsx:82`). Le serveur écoute sur `127.0.0.1`, mais un site malveillant peut lire `http://127.0.0.1:3105/api/state` par **DNS rebinding** (CORS ne protège pas contre ça) et récupérer la clé privée du wallet. C'est le bug le plus grave du projet.

**Correctif** : utiliser `toPublicConfig(this.config)` au lieu de `this.config` dans `handleState`.

### 2. Les secrets Builder/Relayer fuient via SSE — `config.ts:149-163`

```ts
export type PublicBotConfig = Omit<
  BotConfig,
  "privateKey" | "clobApiKey" | "clobSecret" | "clobPassphrase"
>;
```

`toPublicConfig` n'omet **pas** `builderApiKey`, `builderSecret`, `builderPassphrase`, `relayerApiKey`, `relayerApiKeyAddress`. L'événement `config` (émis au démarrage via `bot.ts:75`, rejoué à chaque connexion SSE) les envoie au navigateur. Le type `PublicBotConfig` est censé être "public" — il ne l'est pas.

**Correctif** : étendre l'Omit avec les 5 champs builder/relayer.

### 3. `/api/reset` sans protection CSRF — `server.ts:86`

Un POST form simple (pas besoin de lire la réponse) depuis n'importe quel site peut effacer toute la DB. `/api/redeem` est protégé de fait par le preflight CORS (body JSON), mais le reset ne lit pas le body. Un token CSRF ou un header custom vérifié côté serveur réglerait les deux.

## 🟠 Bugs de logique / propreté

### 4. Dépendance non déclarée — `relayer.ts:16`

```ts
import { BuilderConfig } from "@polymarket/builder-signing-sdk";
```

`@polymarket/builder-signing-sdk` est importé directement mais **absent de `package.json` dependencies** (présent seulement en transitif via `builder-relayer-client` dans le lockfile). Ça compile aujourd'hui grâce au hoisting npm, mais c'est fragile : un `npm ci` propre ou une mise à jour du relayer-client peut casser le build.

**Correctif** : déclarer `@polymarket/builder-signing-sdk` dans `package.json` dependencies.

### 5. `stats_snapshots` écrites, jamais lues — `bot.ts:90`

`resolveAndEmitStats` insère un snapshot toutes les 5 s (~17 280 lignes/jour) mais aucun endpoint ne les lit. `StatsSnapshotRepository` n'a que `insert()`, pas de `recent()` ou `all()`. Le frontend utilise les événements SSE `simulatedStats`. La table grossit sans utilité — soit l'exposer dans `/api/history`, soit la supprimer.

### 6. Incohérence doc/code — `balance.ts:8` vs `index.ts:28`

Le commentaire de `BalanceTracker` dit "works in DRY_RUN too", mais `index.ts:28` ne le démarre **que si `!config.dryRun`**. En dry-run, le panneau "Positions Polymarket" reste vide alors que ça pourrait marcher (il n'utilise que `funderAddress` + API publique). La classe elle-même fonctionnerait en dryRun — c'est le wiring dans `index.ts` qui bloque.

### 7. Fill price live approximé au prix limite — `bot.ts:251`

```ts
fillPrice: order.limitPrice, // GTC: fill au prix limite
```

Faux pour un ordre marketable : le fill réel se fait au bestAsk (meilleur que le limit). `bestAskAtFill` est stocké mais ignoré à cet endroit. L'erreur est **conservatrice** (coût surestimé, PnL pessimiste), donc pas dangereuse — mais le commentaire affirme un fait incorrect.

### 8. `resolvedPositions` sans limite au chargement — `trade-tracker.ts:72`

`loadFromDb` pousse toutes les positions résolues en mémoire sans appliquer `MAX_RESOLVED_IN_MEMORY` (500), contrairement au runtime (`trade-tracker.ts:455`). Une DB ancienne → RAM qui gonfle au démarrage.

### 9. Mapping API probablement faux — `balance.ts:72`

```ts
negRisk: Boolean(p.negativeRisk ?? false)
```

L'interface utilise `negRisk` partout ailleurs ; si l'API data-api renvoie `negRisk` (et non `negativeRisk`), le champ est toujours `false` → le bouton redeem utiliserait le mauvais adapter (standard au lieu de neg-risk). **Non vérifié** — à confirmer avec un appel réel à l'API.

### 10. Spam de logs SSE — `useEventSource.ts:26`

`onerror` log "Connexion SSE perdue" à **chaque** tentative de reconnexion (EventSource se reconnecte automatiquement, onerror se déclenche à chaque échec). Un backend down = centaines de logs d'erreur.

## ✅ Points vérifiés et sains

- **Logique de retry/price levels** : les niveaux de prix servent de fallback quand le niveau précédent est marqué — correct, pas un bug.
- **Garde-fou "not-a-favorite"** dans `bot.ts:329` : redondant avec `strategy.ts` mais justifié (fraîcheur du book entre scan et exécution).
- **`cancelStaleOrders`** : le double `removePostedOrder` est idempotent, pas de fuite.
- **`markOrderFilled`** (frontend) : matche par tokenId mais `maxOpenPositionsPerSide=1` garantit un seul ordre resting par outcome — pas de bug en pratique.
- **Path traversal** `serveStatic` : protégé.
- **`pruneWindowClaims`/`prunePostedOrders`** : regex et seuils cohérents avec le format des slugs.
- **Builds** : backend + frontend compilent sans erreur, `index.html` identique entre `src/dashboard/public` et `dist/dashboard/public`.

## Verdict

**Cohérence : 8/10** — architecture claire, types miroirs backend/frontend bien tenus, builds verts.
**Propreté : 7/10** — code mort présent mais bénin, une dépendance non déclarée.
**Logique : 8/10** — le cœur du trading est solide et bien gardé ; les bugs de logique sont des imprécisions conservatrices, pas des fuites d'argent.
